## 2. หลักการออกแบบ — 6 ข้อที่ห้ามละเมิด

### 2.1 ห้ามแสดงชั่วโมงดิบเป็นคะแนน — ต้องมีตัวหารเสมอ
ชั่วโมงเยอะไม่ได้แปลว่าขยัน (อาจแปลว่าช้า) · ชั่วโมงน้อยไม่ได้แปลว่าเก่ง (อาจแปลว่าได้งานง่าย)
เมตริกหลักจึงต้องเป็น **อัตราส่วนเทียบชั่วโมงมาตรฐาน** ไม่ใช่ผลรวม

### 2.2 ความเร็วต้องแสดงคู่กับคุณภาพในหน้าจอเดียวกันเสมอ
ถ้ารายงานวัดแต่ความเร็ว ช่างจะเร่งงานให้เสร็จแล้วปัญหาไปโผล่ที่ลูกค้า
**ห้ามมีหน้าจอไหนที่แสดงอันดับความเร็วโดยไม่มีคอลัมน์คุณภาพอยู่ข้างๆ** — วิธีวัดคุณภาพดู §5.5

### 2.3 n น้อย = ห้ามสรุป
ช่างที่ทำ 3 จ๊อบในเดือนนั้น ค่าเฉลี่ยไม่มีความหมายทางสถิติ
→ **แสดง n ทุกครั้งที่แสดงค่าเฉลี่ย** · `n < 5` ขึ้นป้าย "ข้อมูลน้อยเกินกว่าจะสรุป" และไม่เข้าการจัดอันดับใดๆ

### 2.4 ความครบของข้อมูลต้องอยู่บนหน้าจอ ไม่ใช่ซ่อนไว้
ช่างลืมกดเริ่ม/กดหยุดเป็นเรื่องปกติ ถ้าไม่บอกว่าข้อมูลครบแค่ไหน ผู้บริหารจะอ่านตัวเลขที่ขาดครึ่งว่าเป็นความจริงทั้งหมด
→ ทุกหน้าต้องมี **ความครบของข้อมูล %** · ต่ำกว่า 70% **ซ่อนการเปรียบเทียบระหว่างช่างทั้งหมด** เหลือแค่ตัวเลขดิบ

### 2.5 ช่างต้องเห็นตัวเลขของตัวเองได้ และตรวจสอบที่มาได้
ถูกวัดโดยไม่รู้ว่าวัดยังไง = ระบบที่คนไม่เชื่อถือและจะหาทางเลี่ยง
→ ช่างเปิดดูของตัวเองได้จากแอป และกดดูได้ว่าตัวเลขมาจากจ๊อบไหนบ้าง (drill-down เป็นข้อบังคับ ไม่ใช่ของแถม)

### 2.6 Goodhart's law — สิ่งที่เอาไปผูกผลตอบแทน จะหยุดเป็นตัววัดที่ดี
พอช่างรู้ว่าถูกวัดด้วยเวลา บางคนจะกดเริ่มทิ้งไว้/ลืมกดหยุดโดยตั้งใจ
**การตัดสินใจไม่ผูกเงินของรอบนี้คือสิ่งที่กันเรื่องนี้ได้ดีที่สุด** — ถ้าวันหนึ่งจะเอาไปผูกคอมมิชชัน
ต้องกลับมาอ่าน §5 ใหม่ทั้งหมดก่อน เพราะเมตริกชุดนี้ออกแบบมาบนสมมติฐานว่า "ไม่มีใครได้เงินเพิ่มจากการปั้นตัวเลข"

## 4. รูปร่างข้อมูล — ตารางเดียว

```
svc_WorkInterval
  Id, LegacyShardKey, LegacyBranchId
  JobId, RepairTaskId(null — เผื่ออนาคต ดู §11)
  TechnicianStaffId, TechnicianName(snapshot)
  Kind: work | pause
  StartedAt(UTC), EndedAt(UTC, null = กำลังเปิดอยู่)
  EndReason
  ShiftSessionId
  RequestId(Guid, unique)           ← กดรัวๆ ต้องไม่ได้หลายช่วง
  IsAutoCapped(bool)                ← ระบบปิดให้เองเพราะลืมกด → ไม่เข้าค่าเฉลี่ย (§5.6)
  CreatedByUserId, EndedByUserId
  EditedByUserId, EditedAt, EditReason   ← null = ไม่เคยถูกแก้
  VoidedAt, VoidReason                   ← ยกเลิกคาบที่ผิดชัดเจน (soft delete)
```

### ทำไมยังต้อง soft delete ทั้งที่ไม่ใช่ข้อมูลการเงินแล้ว
ถ้าลบแถวได้จริง คนที่แก้ตัวเลขตัวเองจะไม่เหลือร่องรอย และ "ความครบของข้อมูล" (§2.4) จะคำนวณไม่ได้
เพราะแยกไม่ออกว่าคาบที่หายไปคือ *ไม่เคยมี* หรือ *ถูกลบ*

### Invariant ที่ต้องบังคับที่ฐานข้อมูล ไม่ใช่แค่ที่ service

```sql
CREATE UNIQUE INDEX UX_WorkInterval_OneOpenPerTech
ON svc_WorkInterval (LegacyShardKey, LegacyBranchId, TechnicianStaffId)
WHERE EndedAt IS NULL;
```

ครอบทั้ง `work` และ `pause` — ช่างจะอยู่ในสถานะ *ทำงาน* หรือ *พัก* เท่านั้น ไม่มีทางทั้งคู่ และไม่มีทางเปิดสองคัน
**ข้อนี้ไม่ได้ผ่อนลงจากฉบับเงิน** เพราะถ้าเปิดซ้อนกันได้ ชั่วโมงจะถูกนับซ้ำและทุกเมตริกใน §5 พังพร้อมกัน

### `EndReason` ที่ต้องมี
`switchedJob` · `paused` · `resumed` · `waitParts` · `sentToQc` · `jobClosed` · `shiftClosed` · `manual` · `autoCapped`

## 5. เมตริก — หัวใจของงานนี้

### 5.1 ชุดเมตริกต่อช่าง ต่อช่วงเวลา

| # | เมตริก | สูตร | อ่านยังไง |
|---|---|---|---|
| 1 | **ประสิทธิภาพเทียบมาตรฐาน** ⭐ | Σ ชม.มาตรฐาน ÷ Σ ชม.ลงมือจริง | `1.0` = ตามมาตรฐาน · `>1` เร็วกว่า · `<1` ช้ากว่า |
| 2 | จ๊อบที่ทำเสร็จ | นับจ๊อบที่ปิดในช่วง | **ปริมาณ ไม่ใช่คะแนน** |
| 3 | เวลาลงมือเฉลี่ยต่อจ๊อบ | Σ `work` ÷ จำนวนจ๊อบ | เทียบได้เฉพาะงานประเภทเดียวกัน |
| 4 | สัดส่วนเวลาพัก | Σ `pause` ÷ (Σ `work` + Σ `pause`) | ดูรูปแบบ ไม่ใช่ตัดสิน |
| 5 | **ชั่วโมงแก้งานหลังเข้า QC** ⭐ | Σ `work` ที่ `StartedAt` อยู่หลังจ๊อบเข้าสถานะ `qc` | คู่คุณภาพหลัก — ดู §5.5 |
| 6 | เวลากว่าจะผ่าน QC | `QcChecklist.SubmittedAt − CreatedAt` | ผ่านฉลุย = ไม่กี่ชม. · ต้องกลับไปแก้ = ข้ามวัน |
| 7 | **รถกลับมาซ้ำใน 30 วัน** | `VehicleId` เดิมเปิดจ๊อบใหม่ภายใน 30 วันหลังปิด | คู่คุณภาพระยะยาว |
| 8 | **ความครบของข้อมูล** | จ๊อบที่มีเวลาครบ ÷ จ๊อบที่รับผิดชอบทั้งหมด | ธงความน่าเชื่อถือ (§2.4) |

⭐ = เมตริกหลักที่ใช้เปรียบเทียบ (ความเร็ว #1 คู่กับคุณภาพ #5 เสมอ ตาม §2.2) · ที่เหลือคือบริบทที่ต้องอ่านประกอบ

### 5.2 เมตริก #1 คำนวณยังไงให้ไม่โกหก

```
ชม.มาตรฐานของจ๊อบ = Σ (StandardHours × Quantity) ของบรรทัด Labor ที่ ApprovalStatus = Approved
                      และ AssignedTechnicianId = ช่างคนนี้
ชม.ลงมือจริง       = Σ (EndedAt − StartedAt) ของ WorkInterval ที่ Kind = work, VoidedAt = null,
                      IsAutoCapped = false
```

**กฎการตัดข้อมูลออก (สำคัญกว่าตัวสูตร):**

1. จ๊อบที่มีบรรทัดค่าแรง **ไม่มี `StandardHours`** (ad-hoc, §3) → **ตัดทั้งจ๊อบออกจากทั้งตัวตั้งและตัวหาร**
   ห้ามนับเป็น 0 ชั่วโมง เพราะจะทำให้ช่างที่ทำงานนอกแคตตาล็อกบ่อยดูช้ากว่าความจริงทันที
   จ๊อบที่ถูกตัดต้องไปโผล่ในหน้า "ความครบของข้อมูล" ไม่ใช่หายเงียบ
2. จ๊อบที่ช่างหลายคนรุมทำพร้อมกัน → **นับเวลาของแต่ละคนแยกกันตามจริง ไม่หาร ไม่เฉลี่ย**
   (ยืนยันกับผู้ใช้ 2026-09-21: *"บันทึกนับไปเลย รุมทำพร้อมกันได้ เพราะวัดที่ระดับตัวช่าง"*) — ดู §5.3
3. คาบ `IsAutoCapped` → ไม่เข้าทั้งสองฝั่ง (§5.6)

### 5.3 ช่างหลายคนรุมคันเดียว — วัดที่ตัวช่าง ไม่ใช่ที่คัน

**ผลดี: ไม่ต้องแก้ schema เลย** invariant ใน §4 คือ "หนึ่งช่วงเปิดต่อ**ช่าง**" ไม่ใช่ "ต่อ**จ๊อบ**"
ช่าง 3 คนรุมคันเดียวจึงเป็น 3 แถวที่เปิดพร้อมกันได้อยู่แล้วโดยธรรมชาติ ไม่ชน unique index

**แต่ตัวหารของเมตริก #1 มีปัญหาที่ต้องจัดการ** — ถ้าช่าง B ไปช่วยจ๊อบที่ไม่มีบรรทัดค่าแรงมอบหมายให้เขาเลย
ชั่วโมงจริงของเขาจะเพิ่มขึ้นโดยที่ชั่วโมงมาตรฐานไม่เพิ่ม = **ยิ่งช่วยเพื่อนยิ่งดูแย่** ซึ่งผิดอย่างชัดเจน
→ แยกชั่วโมงของช่างเป็น 2 ถัง:

| ถัง | นิยาม | ใช้ทำอะไร |
|---|---|---|
| **เวลางานที่รับผิดชอบ** | จ๊อบที่มีบรรทัดค่าแรง `AssignedTechnicianId = เขา` | ← ตัวหารของเมตริก #1 |
| **เวลาช่วยงาน** | จ๊อบที่ลงเวลาแต่ไม่มีบรรทัดของเขาเลย | แสดงแยกเป็นชั่วโมง **ไม่เข้า efficiency** |

"เวลาช่วยงาน" เป็นตัวเลขที่มีประโยชน์ในตัวเอง — คนที่ช่วยงานคนอื่นเยอะคือคนที่ระบบเดิมมองไม่เห็นเลย

> **[RISK] ชั่วโมงรวมของจ๊อบ ≠ เวลาที่รถอยู่ในอู่** พอรุมกันได้ จ๊อบที่ใช้ man-hours 12 ชม. อาจใช้เวลาจริง
> 4 ชม. (ช่าง 3 คน) — **ทุกที่ที่แสดงชั่วโมงของจ๊อบต้องติดป้ายว่าเป็น man-hours** ไม่งั้นผู้บริหารอ่านว่า
> รถจอดรอ 12 ชม. และไปชนกับรายงาน "รอบเวลาทำงาน" เดิมที่วัด wall-clock (§8 ของเอกสารเดิม / §10.3 ที่นี่)

### 5.4 เทียบกับอะไร — ค่ากลางของสาขา ไม่ใช่เป้าที่ตั้งลอยๆ

ไม่มีใครรู้ว่า "ประสิทธิภาพที่ดี" ของอู่นี้คือเท่าไหร่จนกว่าจะเก็บข้อมูลจริงได้สักระยะ
→ **v1 ไม่มีเป้า (target) ใดๆ ทั้งสิ้น** แสดงเทียบ 2 อย่างเท่านั้น:

- **เทียบตัวเอง** — ช่วงนี้เทียบกับช่วงก่อนของช่างคนเดียวกัน (สัญญาณที่มีประโยชน์ที่สุดและแฟร์ที่สุด)
- **เทียบค่ามัธยฐานของสาขา** — ใช้ median ไม่ใช่ mean เพราะจ๊อบใหญ่ผิดปกติคันเดียวลากค่าเฉลี่ยทั้งเดือนได้

ตั้งเป้าเป็นตัวเลข (เช่น "ต้องได้ 0.9 ขึ้นไป") เป็น **[ASSUME] ที่ยังไม่มีข้อมูลรองรับ** — ดู §12

### 5.5 วัดงานแก้ซ้ำโดยไม่ต้องมีสถานะ "ไม่ผ่าน"

ยืนยันกับผู้ใช้ 2026-09-21: **"ถ้าไม่กดผ่าน ความหมายคือยังไม่ผ่าน"** — `QcItemResult` คงไว้แค่
`Pending`/`Pass` ตามเดิม ไม่เพิ่ม `Fail` และไม่ต้องมี UI ตีกลับ

ข้อมูลที่ต้องใช้มีอยู่ครบแล้ว ไม่ต้องเพิ่มคอลัมน์ไหนเลย:

| สัญญาณ | มาจาก | ตีความ |
|---|---|---|
| **ชั่วโมงแก้งานหลังเข้า QC** (#5) | `WorkInterval.StartedAt` > เวลาที่จ๊อบเข้า `qc` | ช่างกลับมาลงมืออีกรอบ = มีของต้องแก้จริง **วัดเป็นชั่วโมงได้ ไม่ใช่แค่นับครั้ง** |
| เวลากว่าจะผ่าน QC (#6) | `QcChecklist.CreatedAt` → `SubmittedAt` | ผ่านรอบแรก = สั้น · ต้องแก้ = ยาว |
| รายการที่ติ๊กผ่านช้าที่สุด | `QcChecklistItem.UpdatedAt` − `QcChecklist.CreatedAt` | ชี้ได้ว่า **รายการซ่อมไหน**ที่มักไม่ผ่านรอบแรก (รวมทั้งสาขา) |

**#5 คือตัวที่แรงที่สุด** เพราะระบบจับเวลาที่กำลังจะสร้างเป็นคนตอบเอง — ไม่ต้องพึ่งการกดปุ่มเพิ่มของใคร
และไม่แตะ process QC ที่ตัดสินใจไปแล้วแม้แต่นิดเดียว

> **ผลต่อ §6:** ต้อง**อนุญาต**ให้กด "เริ่มงาน" ตอนจ๊อบอยู่สถานะ `qc` ได้ (ไม่งั้นช่างที่กลับไปแก้จะกดไม่ได้
> แล้วชั่วโมงแก้งานจะหายไปทั้งก้อน) — คาบที่เปิดตอนสถานะ `qc` ติดธง rework อัตโนมัติ ไม่ต้องให้ใครระบุเอง

### 5.6 คาบที่ลืมปิด (`autoCapped`)

ตัดอัตโนมัติที่ `Shift.EndTime` ของกะนั้น → ติดธง `IsAutoCapped = true`
- **ไม่เข้าการคำนวณเมตริกใดๆ** (เพราะเป็นตัวเลขที่ระบบเดาให้ ไม่ใช่ที่ช่างทำจริง)
- แต่ **นับเข้า "ความครบของข้อมูล"** เป็นฝั่งที่ขาด — จำนวนคาบชนิดนี้เยอะแปลว่ารายงานทั้งหน้าเชื่อได้น้อยลง
- หัวหน้าช่าง/ผู้จัดการแก้เวลาจริงทีหลังได้ พอแก้แล้วธงหลุด คาบนั้นกลับเข้าการคำนวณ (มี `EditedBy` กำกับ)

## 6. ผูกสองทางกับสถานะจ๊อบ

| เหตุการณ์ | ผลต่ออีกฝั่ง |
|---|---|
| กดเริ่มงานครั้งแรก · จ๊อบอยู่ `approved` | ดัน `Approved→InProgress` ผ่าน `JobStateMachine` ปกติ |
| แจ้งรออะไหล่ `InProgress→WaitParts` | ปิดช่วงที่เปิดอยู่ `EndReason=waitParts` |
| ส่ง QC `InProgress→Qc` | ปิดช่วง `EndReason=sentToQc` |
| **QC ผ่าน `Qc→Ready`** | ปิดช่วง `EndReason=sentToQc` — **[เพิ่ม 2026-09-21]** ไม่งั้นคาบที่เปิดตอนกลับมาแก้งาน (§5.5) ค้างเปิดตลอดไป แล้วกลายเป็น `autoCapped` ทุกครั้ง = เมตริกคุณภาพหลักถูกตัดทิ้งอย่างเป็นระบบ |
| ปิดงาน/ยกเลิก (terminal) | ปิดทุกช่วงที่เปิดอยู่ของจ๊อบนั้น `EndReason=jobClosed` |
| ปิดกะ (`AuthService.CloseShift`) | ปิดช่วงของช่างคนนั้น `EndReason=shiftClosed` |
| **กดเริ่มงานตอนจ๊อบอยู่ `qc`** | **อนุญาต** · ไม่ดันสถานะกลับ · คาบนั้นติดธง rework อัตโนมัติ (§5.5) |
| กดเริ่มงานตอนจ๊อบยังซ่อมไม่ได้ (สถานะอื่น) | ปฏิเสธ + บอกว่าต้องผ่านอะไรก่อน (`WORK_JOB_NOT_REPAIRABLE`) |

> การดันสถานะ **ไม่ข้าม guard** — `Approved→InProgress` เปิดให้ `Technician` + `EventSource.Mobile`
> และ guard `HasApprovedLines` เป็น `isComputable` อยู่แล้ว จึงผ่านได้จริงโดยไม่ต้องส่ง reason

> **[BIZ] ทำไมกดเริ่มงานตอน `qc` ได้แต่ไม่ดันสถานะกลับเป็น `InProgress`**
> ระบบไม่มี process ตีกลับ (คำขอผู้ใช้ 2026-09-09) และ `Qc→InProgress` ไม่มี UI ที่ไหนเรียก — จะดันกลับ
> ก็ไม่มีทางเดินกลับมา `qc` ที่ไม่ใช่ manual override · ในทางปฏิบัติช่างเดินไปแก้แล้วกลับมาให้ติ๊กผ่าน
> ซึ่งตรงกับสถานะ `qc` อยู่แล้ว · **ถ้าปฏิเสธการกดเริ่มงานตอน `qc` ชั่วโมงแก้งาน (#5) จะหายไปทั้งก้อน
> ซึ่งเป็นเมตริกคุณภาพตัวเดียวที่วัดได้เป็นชั่วโมง** — ยอมให้เปิดคาบแล้วติดธงดีกว่าบังคับให้ช่างไม่กดปุ่ม

## 7. API

```
POST /api/v1/jobs/{jobId}/work/start    { requestId }
     → เปิดช่วง work + ปิดช่วงเดิมอัตโนมัติใน transaction เดียว
     → คืน { current, closedPrevious }   ← closedPrevious ใช้ขึ้นข้อความยืนยันในแอป

POST /api/v1/jobs/{jobId}/work/pause    { requestId, reason }
POST /api/v1/jobs/{jobId}/work/resume   { requestId }
POST /api/v1/jobs/{jobId}/work/stop     { requestId, reason }

GET  /api/v1/work/current               → ช่วงที่เปิดอยู่ของฉัน + serverNow (กู้สถานะตอนเปิดแอป)
GET  /api/v1/jobs/{jobId}/work          → ทุกคาบของจ๊อบนี้ (ใช้ใน drill-down §8)

PUT  /api/v1/work/intervals/{id}        { startedAt, endedAt, reason }   ← Lead/Manager, ภายใน 7 วัน
DELETE /api/v1/work/intervals/{id}      { reason }                       ← Manager (soft delete)

GET  /api/v1/reports/technician-performance?from=&to=&technicianId=
     → เมตริกทั้ง 7 ตัวของ §5 + coverage + n ของทุกค่าเฉลี่ย
```

**`start` ต้องเป็นคำขอเดียว ห้ามให้ client ยิง stop แล้ว start**
ถ้า start พังหลัง stop สำเร็จ ช่างจะเดินออกไปโดยไม่มีช่วงเปิดและไม่รู้ตัว — ข้อมูลทั้งคาบหาย

**`/reports/technician-performance` ไม่คืน `null` แบบเงียบๆ เมื่อข้อมูลไม่พอ**
ต้องคืนค่าพร้อม `sampleSize` และ `isReliable: false` ให้หน้าจอแสดงเหตุผลได้ (กฎ UI: ทุก state ต้องมีสาเหตุ)

## 8. หน้าจอรายงาน (Web) + สิทธิ์การมองเห็น

### 3 หน้าย่อยใต้เมนู "รายงาน" เดิม

**1 · ภาพรวมทีม** — ตาราง ช่าง × เมตริก §5.1 ทั้ง 8 คอลัมน์ + เวลาช่วยงาน (§5.3)
- เรียงคอลัมน์ได้ (ใช้ `ManagementTable` เดิม) แต่ **ไม่มีเลขอันดับ ไม่มีเหรียญ ไม่มีสีแดง/เขียวตัดสิน**
- แถวที่ `n < 5` เป็นสีจาง + ป้าย "ข้อมูลน้อย" และถูกดันไปท้ายตารางเสมอไม่ว่าจะเรียงด้วยอะไร
- แถบบนสุดบอกความครบของข้อมูลรวม — **ต่ำกว่า 70% ซ่อนคอลัมน์เปรียบเทียบทั้งหมด** เหลือแค่ชั่วโมงดิบ
  พร้อมข้อความว่าทำไมถึงซ่อน (กฎ UI: ห้าม disable เฉยๆ ต้องบอกเหตุผล)

**2 · รายบุคคล** — กราฟเทียบตัวเองย้อนหลัง 6 เดือน + เส้นมัธยฐานสาขา
- **ตารางจ๊อบที่นับอยู่ด้านล่างเสมอ** (เลขจ๊อบ · ทะเบียน · ชม.มาตรฐาน · ชม.จริง · อัตราส่วน)
  คลิกเปิดการ์ดจ๊อบได้ — ข้อนี้คือ §2.5 ไม่ใช่ของแถม
- แสดงจ๊อบที่**ถูกตัดออก**จากการคำนวณแยกอีกกล่อง พร้อมเหตุผล (ไม่มี `StandardHours` / `autoCapped` /
  ถูกยกเลิก / เป็นงานช่วยเพื่อนที่ไม่มีบรรทัดของเขา)

**3 · คุณภาพข้อมูล** — คาบที่ลืมปิด · คาบที่ถูกแก้ (ใครแก้ เหตุผลอะไร) · จ๊อบที่ไม่มีเวลาเลย
- หน้านี้คือหน้าที่หัวหน้าช่างใช้ทำงานจริง ไม่ใช่หน้าที่ผู้บริหารดู — แต่ต้องอยู่ที่เดียวกันเพื่อให้เห็นว่า
  ตัวเลขในหน้า 1 มาจากข้อมูลสภาพไหน

### สิทธิ์ — ต่างจาก `ReportsService` เดิม

| Role | เห็นอะไร |
|---|---|
| `Manager` | ทุกคนในสาขา ทั้ง 3 หน้า |
| `Lead` | ทุกคนในสาขา + หน้าคุณภาพข้อมูล (เป็นคนแก้) |
| `Technician` | **ของตัวเองเท่านั้น** (หน้า 2 ผ่านแอป) |
| `Office` / `Cashier` / `FrontDesk` | **ไม่เห็น** |

> **[BIZ] ตั้งใจให้ต่างจากรายงานอื่น** — `ReportsService` ปัจจุบันเปิดให้ `Manager` + `Office`
> แต่ผลประเมินรายบุคคลเป็นข้อมูลของฝ่ายบุคคล ไม่ใช่ข้อมูลปฏิบัติการที่ธุรการต้องใช้
> ต้องเพิ่ม gate แยก **ห้ามใช้ `ReportsService.Allowed` เดิมซ้ำ**

## 9. Mobile — "โหมดโฟกัส" ไม่ใช่ hard lock

Hard lock (ออกจากหน้าจ๊อบไม่ได้) **จะพังทันที** เพราะช่างต้องใช้แชท ดูใบเสนอราคา ถ่ายรูป ดูอะไหล่ — คนละหน้าทั้งนั้น

- แถบติดหนึบล่างจอ **ทุกหน้า**: `🔧 กำลังทำ 4ขร-2468 · 01:23:45 · [พัก] [ไปที่งาน]`
  (สีต่างเมื่ออยู่ระหว่างพัก + ต้องมีไอคอน/ข้อความ ไม่ใช่สีอย่างเดียว ตามกฎ UI)
- **[เบี่ยงจากเอกสารโดยตั้งใจ 2026-09-21]** เดิมเขียนว่า "เปิดแท็บงานที่ต้องทำ → เด้งเข้าจ๊อบที่กำลังทำ
  อัตโนมัติ" ซึ่งขัดกับบรรทัดถัดไปของ §9 เองที่ว่า "จ๊อบอื่นยังกดดูได้" → ทำเป็น **ปักการ์ดจ๊อบที่กำลังทำไว้
  บนสุดของคิว** แทน (`JobListPage._pinTracking`) ไม่เด้งอัตโนมัติ เพราะแถบจับเวลาที่ติดล่างจอทุกหน้า
  มีปุ่ม "ไปที่งาน" อยู่แล้ว
- จ๊อบอื่นยังกดดูได้ (ช่างต้องเทียบงาน) แต่กด "เริ่มงาน" จะเจอ dialog ยืนยันด้านล่าง
- **กู้สถานะตอนเปิดแอปด้วย `GET /work/current` เสมอ** — ห้ามเชื่อ state ในเครื่อง (online-only)
- **หน้า "ผลงานของฉัน"** — ช่างเปิดดูเมตริกตัวเองได้ (§2.5) ใช้ endpoint เดียวกับเว็บโดยบังคับ `technicianId = ตัวเอง`

### Dialog สลับคัน — ยืนยัน**ก่อน** ไม่ใช่เตือนทีหลัง

```
ช่างกด "เริ่มงาน" ที่คันที่ 2
  → แอปรู้จาก /work/current ว่ามีช่วงเปิดที่คันที่ 1
  → dialog ก่อนยิง API:
```

## 10. ช่องว่างข้อมูลที่ต้องยอมรับก่อนเริ่ม

### 10.1 [แก้แล้ว 2026-09-21] เมตริกคุณภาพไม่ต้องพึ่งสถานะ "ไม่ผ่าน" อีกต่อไป
ร่างก่อนหน้านี้ระบุเป็น `[RISK·สูง]` ว่าเมตริกคุณภาพจะว่างเปล่า เพราะ `Qc→InProgress` (ตีกลับ)
"ไม่มี UI ที่ไหนเรียกเลย" — **ข้อความนั้นผิด** `mobile/lib/core/job_transitions.dart` ประกาศไว้จริง
และเพราะ `primaryFor()` คืนตัวแรกตามลำดับประกาศ ช่างที่เปิดจ๊อบสถานะ `qc` เห็นปุ่ม "ตีกลับให้ช่างแก้ไข"
เป็น**ปุ่มหลัก**ตรึงล่างจอมาตลอด (เว็บไม่มีจริงตามที่บันทึก) — ตรวจ `ActivityEvent` จริงแล้ว
**ไม่เคยมีใครกดสักครั้ง (0 จาก 34 การเปลี่ยนสถานะ)** จึงลบปุ่มออกจากแอป 2026-09-21 ตามคำตอบของผู้ใช้
`JobStateMachine.cs` ฝั่ง backend ยังคง transition นี้ไว้ แต่ไม่มีใครเรียกแล้วจริงๆ

ผู้ใช้ยืนยัน 2026-09-21 ว่า **"ไม่กดผ่าน = ยังไม่ผ่าน"** → ไม่ต้องเพิ่ม `QcItemResult.Fail`
และไม่ต้องแตะ process QC เลย เพราะวัดจากเวลาแทนได้ทั้งหมด (§5.5)
**`Qc→InProgress` จึงไม่ถูกใช้ในงานนี้เลย** ปล่อยให้เป็น transition ที่ไม่มีใครเรียกต่อไปตามเดิม

### 10.2 เมตริก #7 (รถกลับมาซ้ำ) โยงคนผิดได้
อาจเป็นคนละอาการ/คนละระบบกับที่ช่างคนนั้นซ่อม
→ v1 **แสดงเป็นตัวเลขให้คลิกดูรายการจ๊อบได้ ห้ามสรุปเป็นคะแนน** ให้คนอ่านตัดสินเอง

### 10.3 man-hours ปนกับ wall-clock ได้ง่ายมาก
พอช่างรุมคันเดียวกันได้ (§5.3) ชั่วโมงรวมของจ๊อบจะมากกว่าเวลาที่รถอยู่ในอู่จริง และ **รายงาน
"รอบเวลาทำงาน" ที่มีอยู่แล้ววัด wall-clock** (จ๊อบค้างในสถานะไหนนานเท่าไหร่ จาก `ActivityEvent`)
ตัวเลขสองชุดนี้ต่างกันมากและถูกทั้งคู่ — **ติดป้ายให้ชัดทุกจุด** ไม่งั้นคนอ่านสรุปผิดแน่นอน

### 10.4 ไม่มี "ความยากของงาน"
ระบบไม่มี complexity/skill level → เทียบข้ามประเภทงานไม่ได้
`StandardHours` ช่วยชดเชยได้บางส่วน (งานยากมีชั่วโมงมาตรฐานสูงกว่า) แต่ไม่ครอบคลุมเรื่องรถรุ่นยาก/อะไหล่หายาก

### Tests ที่ต้องมี (อย่างน้อย)

**ชั้นเก็บเวลา**
- เปิดช่วงซ้อนกันไม่ได้ (ชน unique index จริง ไม่ใช่แค่ service เช็ค)
- `start` คันใหม่ปิดคันเดิมใน transaction เดียว — และถ้า start ล้ม คันเดิมต้องยังเปิดอยู่
- `RequestId` เดิมยิงซ้ำไม่เกิดช่วงใหม่
- pause/resume ได้เวลา `work` ถูกต้อง ไม่นับช่วง `pause`
- เปลี่ยนสถานะจ๊อบทุกเส้นทางใน §6 ปิดช่วงให้จริง · ปิดกะปิดช่วงค้างให้จริง
- ช่างแก้เวลาตัวเองไม่ได้ · เกิน 7 วันแก้ไม่ได้ · void แล้วไม่เข้าการคำนวณแต่ยังอยู่ในตาราง

**ชั้นรายงาน — สำคัญไม่แพ้กัน**
- จ๊อบที่บรรทัดค่าแรงไม่มี `StandardHours` **ถูกตัดออกทั้งจ๊อบ ไม่ถูกนับเป็น 0** (§5.2)
- คาบ `autoCapped` ไม่เข้าเมตริก แต่ทำให้ coverage ลดลงจริง
- **ช่าง 3 คนเปิดช่วงในจ๊อบเดียวพร้อมกันได้จริง** (ไม่ชน unique index) และได้เวลาคนละก้อนถูกต้อง (§5.3)
- **ช่างที่ลงเวลาในจ๊อบที่ไม่มีบรรทัดของตัวเอง → เข้าถัง "เวลาช่วยงาน" ไม่ทำให้ efficiency แย่ลง** (§5.3)
- **คาบที่เปิดหลังจ๊อบเข้า `qc` ถูกนับเป็นชั่วโมงแก้งาน (#5) และไม่ดันสถานะจ๊อบกลับ** (§5.5, §6)
- คาบก่อนเข้า `qc` ไม่ถูกนับเป็นชั่วโมงแก้งาน (กันนับผิดฝั่งเส้นแบ่งเวลา)
- `n < 5` คืน `isReliable: false`
- coverage < 70% ไม่คืนค่าเปรียบเทียบระหว่างช่าง
- ช่างเรียก endpoint ด้วย `technicianId` ของคนอื่น → 403 · `Office` เรียก → 403
