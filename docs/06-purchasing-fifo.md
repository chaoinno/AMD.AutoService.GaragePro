# จัดซื้อ PR / PO และ Stock FIFO

เปิดเว็บ `/purchasing` และ `/inventory` ด้วยบทบาท Manager หรือ Office ใช้ shard และสาขาจาก JWT อัตโนมัติ ทุกเส้นมีคำอธิบายภาษาไทยใน Swagger

## การใช้งาน

1. สร้าง PR เลือกคลัง วันที่ต้องการ และรายการอะไหล่ ระบบออกเลขเอกสารเมื่อบันทึก
2. ส่ง PR ขออนุมัติ ผู้จัดการอนุมัติ หรือส่งกลับแก้ไขพร้อมเหตุผล
3. เลือกซัพพลายเออร์เพื่อแปลง PR เป็น PO ฉบับร่าง หนึ่ง PR แปลงได้หนึ่ง PO ทั้งรายการและจำนวนตามที่อนุมัติ ราคาซื้อแก้ใน PO ร่างได้
4. ส่ง PO ขออนุมัติ แล้วกดยืนยันส่งสั่งซื้อ ระบบเพิ่ม OnOrder แต่ไม่เพิ่มจำนวนพร้อมใช้ สามารถสร้าง PO โดยตรงได้ด้วย
5. รับสินค้าโดยระบุเลขใบส่งของ จำนวนของดี/ชำรุด และราคาที่รับจริง รับบางส่วนได้ ของชำรุดไม่สร้างล็อตพร้อมใช้ รับครบรวมของชำรุดแล้ว PO เป็น complete
6. เบิกจากหน้าสต็อก เลือกคลัง จำนวน และเหตุผล ระบบตัดล็อตตาม ReceivedAt แล้ว Id คำนวณต้นทุนจากล็อตจริง และสร้าง ISS พร้อมประวัติแยกล็อต

## สถานะและสิทธิ์

| เอกสาร | เส้นทาง |
| --- | --- |
| PR | draft → pending → approved → converted; pending ส่งกลับ draft ได้ |
| PO | draft → pending → approved → sent → partial → complete; pending ส่งกลับ draft ได้ |
| ยกเลิก | บังคับเหตุผล PR ที่ converted และ PO ที่ complete ยกเลิกไม่ได้ |

Manager และ Office สร้าง/อ่าน/แก้ร่าง/ส่งเอกสารและรับสินค้าได้ PR ต้องให้ Manager อนุมัติ PO ที่เกินวงเงินต้องให้ Manager อนุมัติ ราคาต่อหน่วยและมูลค่าของเอกสารจัดซื้อเปิดให้ทั้งสองบทบาทใช้ทำรายการ ส่วนต้นทุนล็อต FIFO มูลค่าสต็อก และต้นทุนเบิกเปิดเฉพาะ Manager

วงเงินเริ่มต้น 10,000 บาทตามสมมติฐานของ prototype ปรับได้ด้วย `Purchasing:ManagerApprovalThreshold` ยอดเอกสารในรุ่นนี้เป็นมูลค่าสินค้าก่อนภาษี ยังไม่มี VAT/ส่วนลด/ค่าขนส่งหรือการชำระหนี้

คำสั่งส่ง PO บันทึกสถานะสั่งซื้อในระบบ ยังไม่ส่งอีเมลหรือเชื่อมระบบซัพพลายเออร์ภายนอก

## ยอดยกมาและบัญชีสต็อก

- สินค้าที่มียอด OnHand หรือ Damaged เดิม ต้องให้ผู้จัดการตั้งยอดยกมาครั้งเดียว ยืนยันคลัง ต้นทุน จำนวนเดิม และเหตุผล จึงรับเข้าผ่าน FIFO ได้ ไม่มีการเพิ่มยอดเดิมซ้ำ
- สินค้าที่ยอดเดิมเป็นศูนย์เริ่ม FIFO ได้เมื่อรับ GRN ครั้งแรก
- คงเหลือ OnHand คือของดีทั้งหมดในสาขา ส่วน Damaged เก็บแยก จำนวนพร้อมใช้คือ OnHand − Reserved ไม่รวม OnOrder หรือ Damaged
- แต่ละล็อตผูกคลังและสินค้า การเบิกต้องมีของดีในคลังเพียงพอ และไม่เกินจำนวนพร้อมใช้ทั้งสาขา
- การยกเลิก PO ที่รับบางส่วนลดเฉพาะ OnOrder ที่ยังค้าง ยอดที่รับแล้วและต้นทุนล็อตคงเดิม
- เมื่อเริ่ม FIFO หรือส่ง PO ของสินค้านั้นแล้ว API ล็อกการแก้ยอดสต็อก ประเภท และหน่วยนับโดยตรงในหน้าสินค้า การแก้ชื่อ/ราคาแคตตาล็อกไม่เปลี่ยนต้นทุนล็อตเก่า
- รายการเคลื่อนไหวมีเอกสาร คลัง ล็อต จำนวน ก่อน/หลัง ต้นทุน เหตุผล ผู้ทำ และเวลา โดยก่อน/หลังเป็นยอดของดีรวมทั้งสาขา หน้ารายละเอียดแสดงล่าสุด 200 รายการ

## การป้องกันบันทึกซ้ำและการแข่งขัน

ทุกการเขียน PR/PO/GRN/FIFO ทำใน SQL transaction เดียว รวม ActivityEvent ใช้ transaction-owned `sp_getapplock` แยกตาม shard/สาขา เพื่อเรียงการเปลี่ยนยอดและออกเลขเอกสาร การ retry ของ EF อ่านข้อมูลใหม่ทั้งหมด มี unique indexes และ rowversion กำกับ

แก้ไข/เปลี่ยนสถานะ/แปลงเอกสารต้องส่ง `Version` จาก GET ล่าสุด หากเปลี่ยนแล้วคืน 409

รับสินค้าและเบิกต้องมี `RequestId` (UUID) การ retry ใช้ UUID และ payload เดิมจะคืนผลเดิม หาก UUID เดิมแต่เนื้อหาต่างคืน 409 เว็บเก็บคำขอที่ยังไม่ทราบผลไว้ใน sessionStorage เพื่อให้กดตรวจสอบซ้ำหลังปิด popup หรือ reload ได้

สินค้าใช้จำนวนเต็มตามโครงสร้างแคตตาล็อกเดิม จำนวนต่อบรรทัด 1–1,000,000 ราคาไม่ติดลบทศนิยมไม่เกิน 2 ตำแหน่ง รับเกิน PO ถูกปฏิเสธ ราคาที่ต่างจาก PO ต้องให้ Manager ยืนยันพร้อมเหตุผล ของชำรุดต้องระบุหมายเหตุ
