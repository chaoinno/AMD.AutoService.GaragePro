# จัดซื้อ PR / PO และ Stock FIFO

เปิดเว็บ `/purchasing` และ `/inventory` ด้วยบทบาท Manager หรือ Office ใช้ shard และสาขาจาก JWT อัตโนมัติ ทุกเส้นมีคำอธิบายภาษาไทยใน Swagger

## การใช้งาน

1. สร้าง PR เลือกคลัง วันที่ต้องการ รายการอะไหล่ และมี VAT 7% / ไม่มี VAT ตามเงื่อนไขผู้ขาย ระบบออกเลขเอกสารเมื่อบันทึก ราคาต่อหน่วยเป็นราคาก่อน VAT
2. ส่ง PR ขออนุมัติ ผู้จัดการอนุมัติด้วย PIN สาขา 4 หลัก หรือส่งกลับแก้ไขพร้อมเหตุผล
3. เลือกซัพพลายเออร์เพื่อแปลง PR เป็น PO ที่อนุมัติแล้ว หนึ่ง PR แปลงได้หนึ่ง PO โดยรับรายการ ราคา VAT และผลอนุมัติจาก PR
4. กดยืนยันส่งสั่งซื้อ PO ระบบเพิ่ม OnOrder แต่ไม่เพิ่มจำนวนพร้อมใช้ สามารถสร้าง PO โดยตรงและส่งขออนุมัติได้ด้วย การเพิ่ม/แก้/ลบสินค้า หรือเปลี่ยน VAT หลังอนุมัติ ต้องส่งขออนุมัติใหม่เฉพาะส่วนที่เปลี่ยน รายการเดิมคงผลอนุมัติไว้
5. รับสินค้าโดยระบุเลขใบส่งของ จำนวนของดี/ชำรุด และราคาที่รับจริง รับบางส่วนได้ ของชำรุดไม่สร้างล็อตพร้อมใช้ รับครบรวมของชำรุดแล้ว PO เป็น complete
6. เบิกจากหน้าสต็อก เลือกคลัง จำนวน และเหตุผล ระบบตัดล็อตตาม ReceivedAt แล้ว Id คำนวณต้นทุนจากล็อตจริง และสร้าง ISS พร้อมประวัติแยกล็อต
7. เบิกหลายรายการในใบเดียว (ผูก job ได้) — ใช้ปุ่ม "สร้างใบเบิกสินค้า" ในหน้าใบสั่งงานซ่อม (JobCardModal ขั้น "เบิกสินค้า/ดำเนินการซ่อม") เลือกคลัง ผู้เบิก (พนักงาน active ของสาขา) เหตุผล และสินค้าได้หลายรายการ ออกเลขที่ขึ้นต้น `WD-` แยกจาก `ISS-` เดิม พิมพ์ใบเบิกได้ (มีช่องเซ็นผู้เบิก/ผู้จ่าย ไม่มีเซ็นดิจิทัล) — เบิกทีละรายการจากหน้าสต็อกเดิม (ข้อ 6) ยังใช้งานคู่ขนานได้เหมือนเดิม
   - **[เพิ่ม 2026-10-02] ใบเบิกที่ผูก job เบิกได้ตามรายการที่ลูกค้าอนุมัติเท่านั้น** — เพิ่มสินค้าอื่นไม่ได้ เบิกเกินยอดคงเหลือไม่ได้ · **เบิกบางส่วนได้**
     รายการมาจาก `GET /api/v1/inventory/withdrawals/by-job/{jobId}/plan` = บรรทัดอะไหล่ที่ `Approved` ของใบเสนอราคาที่**เซ็นแล้ว**
     ทุกใบ (ไม่นับ Superseded) รวมตามรหัสแคตตาล็อก หักยอดที่เบิกด้วยใบเบิกก่อนหน้าของ job เดียวกัน (จำนวนทศนิยมปัดต่อบรรทัด ขั้นต่ำ 1)
     · `POST /withdrawals` ที่มี `jobId` ส่งได้เฉพาะบรรทัดที่ยังเหลือ จำนวน 1..ยอดคงเหลือ (ไม่ต้องครบทุกรายการ — ส่วนที่เหลือเบิกต่อใบถัดไป)
     — ไม่งั้นได้ `WITHDRAWAL_NOT_APPROVED` (สินค้าที่ไม่ได้อนุมัติ/เบิกครบแล้ว) · `WITHDRAWAL_EXCEEDS_APPROVED` (เกินยอดคงเหลือ) ·
     `WITHDRAWAL_NOTHING_TO_WITHDRAW` (ไม่มีอะไรเหลือ) — ทั้งหมด 422 · replay ด้วย RequestId เดิมยังคืนผลเดิมเพราะตรวจก่อนกฎนี้
     · รายการนอกแคตตาล็อก และรหัสที่ไม่มีในแคตตาล็อก/ยังไม่ตั้งยอด FIFO **ไม่อยู่ในใบเบิก** (แจ้งแยกบนหน้าจอ) ไม่งั้น job นั้นจะสร้างใบเบิกไม่ได้เลย
     · หน้าเว็บ: แถวลบไม่ได้ แต่ใส่จำนวน 0..คงเหลือได้ (0 = ยังไม่เบิกรอบนี้) ค่าเริ่มต้น = min(คงเหลือ, พร้อมใช้)
     · ใบเบิกที่ไม่ผูก job (`jobId = null`) ยังเลือกสินค้าเองได้ตามเดิม (ปัจจุบันไม่มีหน้าเว็บเรียกแบบนี้)

## สถานะและสิทธิ์

| เอกสาร | เส้นทาง |
| --- | --- |
| PR | draft → pending → approved → converted; pending ส่งกลับ draft ได้ |
| PO จาก PR | รับผลอนุมัติ PR เป็น approved → sent → partial → complete |
| PO โดยตรง / แก้ไข | draft → pending → approved → sent → partial → complete; pending ส่งกลับ draft ได้ |
| ยกเลิก | บังคับเหตุผล PR ที่ converted และ PO ที่ complete ยกเลิกไม่ได้ |

Manager และ Office สร้าง/อ่าน/แก้ร่าง/ส่งเอกสารและรับสินค้าได้ PR ต้องให้ Manager อนุมัติ PO ที่เกินวงเงินต้องให้ Manager อนุมัติ ราคาต่อหน่วยและมูลค่าของเอกสารจัดซื้อเปิดให้ทั้งสองบทบาทใช้ทำรายการ ส่วนต้นทุนล็อต FIFO มูลค่าสต็อก และต้นทุนเบิกเปิดเฉพาะ Manager

วงเงินเริ่มต้น 10,000 บาทตามสมมติฐานของ prototype ปรับได้ด้วย `Purchasing:ManagerApprovalThreshold` ใช้ยอดสุทธิรวม VAT ในการตรวจวงเงิน ยังไม่มีส่วนลด/ค่าขนส่งหรือการชำระหนี้

คำสั่งส่ง PO บันทึกสถานะสั่งซื้อในระบบ ยังไม่ส่งอีเมลหรือเชื่อมระบบซัพพลายเออร์ภายนอก

## ยอดยกมาและบัญชีสต็อก

- สินค้าที่มียอด OnHand หรือ Damaged เดิม ต้องให้ผู้จัดการตั้งยอดยกมาครั้งเดียว ยืนยันคลัง ต้นทุน จำนวนเดิม และเหตุผล จึงรับเข้าผ่าน FIFO ได้ ไม่มีการเพิ่มยอดเดิมซ้ำ
- สินค้าที่ยอดเดิมเป็นศูนย์เริ่ม FIFO ได้เมื่อรับ GRN ครั้งแรก
- คงเหลือ OnHand คือของดีทั้งหมดในสาขา ส่วน Damaged เก็บแยก จำนวนพร้อมใช้คือ OnHand − Reserved ไม่รวม OnOrder หรือ Damaged
- แต่ละล็อตผูกคลังและสินค้า การเบิกต้องมีของดีในคลังเพียงพอ และไม่เกินจำนวนพร้อมใช้ทั้งสาขา
- การยกเลิก PO ที่รับบางส่วนลดเฉพาะ OnOrder ที่ยังค้าง ยอดที่รับแล้วและต้นทุนล็อตคงเดิม
- เมื่อเริ่ม FIFO หรือส่ง PO ของสินค้านั้นแล้ว API ล็อกการแก้ยอดสต็อก ประเภท และหน่วยนับโดยตรงในหน้าสินค้า การแก้ชื่อ/ราคาแคตตาล็อกไม่เปลี่ยนต้นทุนล็อตเก่า
- รายการเคลื่อนไหวมีเอกสาร คลัง ล็อต จำนวน ก่อน/หลัง ต้นทุน เหตุผล ผู้ทำ และเวลา โดยก่อน/หลังเป็นยอดของดีรวมทั้งสาขา หน้ารายละเอียดแสดงล่าสุด 200 รายการ

## การป้องกันบันทึกซ้ำและการแข่งขัน

ทุกการเขียน PR/PO/GRN/FIFO ทำใน SQL transaction เดียว รวม ActivityEvent ใช้ transaction-owned `sp_getapplock` แยกตาม shard/สาขา เพื่อเรียงการเปลี่ยนยอดและออกเลขเอกสาร การ retry ของ EF อ่านข้อมูลใหม่ทั้งหมด มี unique indexes และ rowversion กำกับ

แก้ไข/เปลี่ยนสถานะ/แปลงเอกสารต้องส่ง `Version` จาก GET ล่าสุด หากเปลี่ยนแล้วคืน 409

รับสินค้าและเบิกต้องมี `RequestId` (UUID) การ retry ใช้ UUID และ payload เดิมจะคืนผลเดิม หาก UUID เดิมแต่เนื้อหาต่างคืน 409 เว็บเก็บคำขอที่ยังไม่ทราบผลไว้ใน sessionStorage เพื่อให้กดตรวจสอบซ้ำหลังปิด popup หรือ reload ได้

สินค้าใช้จำนวนเต็มตามโครงสร้างแคตตาล็อกเดิม จำนวนต่อบรรทัด 1–1,000,000 ราคาไม่ติดลบทศนิยมไม่เกิน 2 ตำแหน่ง รับเกิน PO ถูกปฏิเสธ ราคาที่ต่างจาก PO ต้องให้ Manager ยืนยันพร้อมเหตุผล ของชำรุดต้องระบุหมายเหตุ

## VAT ในเอกสารจัดซื้อ

กำหนด VAT ระดับเอกสารใน PR ก่อนอนุมัติงบ และส่งค่าต่อไป PO โดยอัตโนมัติ PO โดยตรงเลือกได้เช่นกัน ค่าเริ่มต้นและเอกสารเก่าเป็นไม่มี VAT เพื่อคงยอดเดิม เมื่อมี VAT ระบบคิดจากผลรวมจำนวน × ราคาก่อนภาษี แล้วปัด VAT เป็น 2 ตำแหน่งด้วย AwayFromZero เพียงครั้งเดียว ยอดสุทธิ = มูลค่าก่อนภาษี + VAT วงเงินอนุมัติธุรการใช้ยอดสุทธิรวม VAT หน้ารายการ รายละเอียด เอกสารพิมพ์ และ Excel แสดงยอดสอดคล้องกัน

เก็บอัตรา VAT (0.07) ในเอกสารและเก็บค่า VAT ที่อนุมัติไว้ เปลี่ยน VAT แล้วเอกสารกลับเป็นร่าง ต้องขออนุมัติด้วย PIN ก่อนส่งสั่งซื้ออีกครั้ง การอนุมัติ VAT ของ PR ส่งผลเฉพาะค่า VAT ที่ตรงกันใน PO ไม่อนุมัติรายการแก้ไขอื่นของ PO โดยอัตโนมัติ ราคาของล็อต FIFO ยังคงเป็นราคาต่อหน่วยก่อนภาษีตามราคาในใบรับสินค้า

การเลือกมี/ไม่มี VAT เป็นเงื่อนไขราคาในเอกสารจัดซื้อ ไม่ใช่การสร้างหรือบันทึกภาษีซื้อทางบัญชี การใช้ภาษีซื้อยังต้องตรวจใบกำกับภาษีของผู้ขายในกระบวนการบัญชี ซึ่งระบบนี้ยังไม่ได้ครอบคลุม อ้างอิง [ข้อหารือใบสั่งซื้อของกรมสรรพากร](https://www.rd.go.th/40710.html) และ [มาตรา 82/4–82/5](https://www.rd.go.th/5206.html) ตรวจแหล่งข้อมูลวันที่ 2 ตุลาคม 2569

รัน unit tests ด้วย `dotnet test backend/AMD.AutoService.GaragePro.Tests --filter FullyQualifiedName~PurchasingServiceTests` และ regression ของ CatalogServiceTests

SQL integration test: ตั้ง environment variable `GARAGEPRO_PURCHASING_SQL_CONNECTION` เป็น connection ของ ServiceDb ที่ migrate แล้ว จากนั้นรัน `dotnet test backend/AMD.AutoService.GaragePro.Tests --filter FullyQualifiedName~PurchasingSqlTests` ใช้ shard ทดสอบสุ่มและลบเฉพาะ fixture ของการรันนั้นใน finally ทดสอบวงจร PR/PO จริง การแก้ร่าง rowversion รับซ้ำพร้อมกัน เบิกพร้อมกัน FIFO ข้ามล็อต และแยก shard
