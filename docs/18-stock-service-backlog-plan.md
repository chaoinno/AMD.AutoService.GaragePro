## [1] กำหนด min-max ให้สต็อก FIFO + สีเตือน + ตัวเลขที่เมนู

**ตัดสินใจแล้ว**
- เตือนเมื่อ **พร้อมใช้ ≤ min** · พร้อมใช้ = `OnHand − Reserved` (กฎข้อ 6 — ไม่รวม OnOrder/Damaged) · ระดับเดียว ไม่มีเกณฑ์ % ล่วงหน้า
- **max ใช้คำนวณจำนวนแนะนำให้สั่งเท่านั้น** = `max − พร้อมใช้ − OnOrder` (ไม่ต่ำกว่า 0) · ไม่เตือนเมื่อเกิน max · ไม่สร้าง PR ให้เอง
- ตั้งค่าและเห็นตัวเลข = **ธุรการ/ผู้จัดการ** (สิทธิ์เดียวกับโมดูลจัดซื้อ `PurchasingService.Access()`)

**Backend**
- `CatalogItem` เพิ่ม `MinStock int?` / `MaxStock int?` (null = ไม่ได้ตั้ง ไม่ถูกนับ) · migration `AddCatalogItemMinMax` (nullable 2 คอลัมน์)
- กฎรวมที่เดียว `Domain/Common/StockLevel.cs`: `Available` · `IsBelowMin` · `SuggestedOrderQty` — ใช้ทั้ง query นับ, DTO และเทสต์
- ตั้งค่าได้เฉพาะสินค้า `Type = Part` และ `StockManaged` · ตรวจ `0 ≤ min ≤ max` (`CATALOG_VALIDATION`) · ไม่ผูกกับการล็อกยอด FIFO
  (`PurchasingLocked` ล็อกยอดคงเหลือ ไม่ใช่ค่าตั้ง)
- `GET /api/v1/inventory/low-stock/count` → จำนวนสินค้าที่ `IsBelowMin` ในสาขา (ไม่นับสินค้าที่ไม่ได้ตั้ง min · ไม่นับ inactive)
- รายการสต็อก/สินค้าเพิ่มฟิลด์ `minStock` `maxStock` `belowMin` `suggestedOrderQty` และตัวกรอง "ถึงจุดต่ำสุด"
- **ตัวกรองเดิม `LowStockOnly` ("ของหมด/ถูกจองหมด" = พร้อมใช้ ≤ 0) คงความหมายเดิม** แยกเป็นคนละตัวกรอง ไม่เปลี่ยนพฤติกรรมเดิมแบบเงียบๆ
- endpoint ใหม่สืบทอด `[RequireFeature]` ของสต็อก (sp1 ทดลองใช้ถูกล็อก)

**เว็บ**
- ฟอร์มสินค้า: ช่อง min/max (เฉพาะอะไหล่ที่คุมสต็อก) + ข้อความบอกสูตร
- หน้าสต็อก FIFO และรายการสินค้า: แถวที่ถึงจุดต่ำสุด = พื้นเหลือง + ไอคอนเตือน + ป้าย "ถึงจุดต่ำสุด" (สี+ไอคอน+ข้อความตามกฎ UI) · คอลัมน์ min · max · แนะนำให้สั่ง
- เมนู "สต็อก FIFO" มีตัวเลขเหมือน PR/PO · queryKey ขึ้นต้น `'purchase-count'` เพื่อให้ `usePurchasingRefresh` invalidate หลังรับของ/เบิก/คืน/ขายหน้าร้าน
- เรียงคอลัมน์ใหม่ด้วย `ManagementTable` + `accessorFn` ตามกฎตาราง

**เทสต์**: `StockLevel` (ไม่ตั้ง min · เท่ากับ min · Reserved ทำให้ถึง min · แนะนำสั่งไม่ติดลบ) · นับเฉพาะสาขาปัจจุบัน · validation min > max ·
role อื่นได้ 403

**ยังไม่ทำ**: เตือนเกิน max · สร้าง PR จากรายการต่ำกว่า min · แจ้งเตือนในกระดิ่ง (ตัวเลขเมนูพอแล้ว) · ค่า min-max ต่อคลัง (ตอนนี้ต่อสินค้าต่อสาขา)

## [2] นัดเข้ารับบริการครั้งถัดไปได้หลายรายการ

**ตัดสินใจแล้ว**
- เลือกจาก **รายการตั้งต้นของสาขา** (มีไมล์/เดือนตั้งต้น) แล้วแก้ค่าต่อคันได้ + **พิมพ์รายการเองได้**
- ก่อนเซ็นส่งมอบต้องมี **อย่างน้อย 1 รายการ** (กฎข้อ 23 คงเดิม · ไมล์ส่งมอบยังบังคับ)

**Backend**
- ตารางใหม่ `svc_ServiceReminderTemplate` (shard/สาขา · `Name` · `DefaultMileageInterval` · `DefaultMonths` · `SortOrder` · `IsActive`)
  · จัดการได้เฉพาะผู้จัดการ (`MASTER_DATA_MANAGE_FORBIDDEN` แบบเทมเพลตใบเสนอราคา) · สร้างชุดตั้งต้นให้เองตอนสาขาเรียกครั้งแรก
  · ชุดตั้งต้น (ยืนยันแล้ว 2026-10-25): น้ำมันเครื่อง 10,000 กม./6 เดือน · กรองน้ำมันเครื่อง 10,000/6 · น้ำมันเกียร์ 40,000/24 ·
    น้ำมันเบรก 40,000/24 · กรองอากาศ 20,000/12 · เช็คระยะ 10,000/6
- ตารางใหม่ `svc_HandoverServiceItem` (`HandoverRecordId` · `TemplateId?` · `Name` snapshot · `NextServiceMileage` · `NextServiceMonths` ·
  `NextServiceDueOn date` · `SortOrder`)
- **backfill**: ใบส่งมอบเดิมที่มี `NextService*` → 1 แถวชื่อ "เช็คระยะ" · คอลัมน์เดิมใน `HandoverRecord` **คงไว้แต่เลิกใช้** (แบบ `DepositAmount`) ไม่ drop
- `PUT .../handover/service-info` body ใหม่ `{ mileageAtHandover, items: [{ templateId?, name, nextServiceMileage, nextServiceMonths }] }`
  · **ยังรับ body เดิม** (`nextServiceMileage`/`nextServiceMonths` ตัวเดียว) แปลงเป็น 1 รายการชื่อ "เช็คระยะ" — แอปรุ่นที่อยู่บน store ต้องส่งมอบรถได้ต่อ
    (บทเรียน: deploy backend ก่อนแอปถึงมือผู้ใช้เคยทำให้ส่งมอบไม่ได้)
- กฎต่อรายการ: ไมล์นัด > ไมล์ส่งมอบ · เดือน 1–24 · ชื่อไม่ว่าง ไม่ซ้ำในใบเดียว (ตัดช่องว่าง) · ไม่เกิน 10 รายการ (เพดานกันข้อมูลผิดปกติ ไม่ใช่กฎธุรกิจ) ·
  `SubmitAsync` คำนวณ `NextServiceDueOn` ทุกรายการใหม่จาก `SubmittedAt` (`ServiceSchedule` เดิม) · ล็อกพร้อมใบส่งมอบ
- `HandoverDto` คืน `serviceItems[]` + คงฟิลด์เดิมเป็นค่าของรายการที่ครบเร็วที่สุด (ให้แอปรุ่นเก่าแสดงได้)
- รายงาน `service-due`: 1 แถวต่อรถ · วันนัดของรถ = รายการที่ครบเร็วที่สุด · แสดงรายการทั้งหมดใต้แถว · กฎตัดคันที่กลับมาเปิดจ๊อบเดิมไม่เปลี่ยน
- `reports/vehicle-history` แสดงรายการนัดทุกตัว

**เว็บ**: `HandoverServiceInfoSection` เป็นรายการแถว + ปุ่ม "เพิ่มรายการ" (เลือกจากรายการตั้งต้น หรือพิมพ์เอง) · ลบแถวได้จนกว่าจะเซ็น ·
ใบส่งมอบพิมพ์เป็นตาราง (รายการ · ไมล์ที่นัด · วันที่นัด) · หน้า Master Data "รายการนัดบริการ" · Excel รายงานใกล้ครบรอบมีคอลัมน์รายการ

**มือถือ**: `handover_service_info.dart` เป็นรายการแบบเดียวกัน · ส่ง body ใหม่ · ปล่อยแอปรุ่นใหม่

**เทสต์**: แต่ละรายการคำนวณวันนัดถูก (ข้ามเดือน/ปีอธิกสุรทิน) · body เดิมยังใช้ได้ · ไม่มีรายการ → `HANDOVER_SERVICE_INFO_REQUIRED` ·

## [3] รายงานการเบิกอะไหล่

**ตัดสินใจแล้ว**
- 3 มุมมอง: **รายใบเบิก** · **สรุปตามสินค้า** (กดดูได้ว่าเอาไปใช้กับจ๊อบไหน เมื่อไหร่ หรือขายออก POS เมื่อไหร่) · **สรุปตามช่างผู้เบิก**
- เปิดได้ = ธุรการ/ผู้จัดการ · ต้นทุนเป็น `null` ที่ server สำหรับ role ที่ `CanSeeCost = false` (กฎข้อ 7)

**Backend** `GET /api/v1/reports/stock-usage?fromDate=&toDate=&view=documents|items|requesters&warehouseId=&catalogItemId=&requesterStaffId=&source=`
- แหล่งข้อมูล `StockMovement` ประเภท `issue` (ผูก job / เบิกหน้าสต็อก) · `issue-return` (จาก [4]) · `sale` · `sale-void`
- `source` = `job` · `manual` (ISS- ไม่ผูก job) · `pos`
- **รายใบเบิก**: group ด้วย `OperationId` → วันที่ · เลข WD-/ISS- · เลขจ๊อบ + ทะเบียน · ผู้เบิก · ผู้จ่าย · จำนวนรายการ · จำนวนสุทธิหลังคืน · ต้นทุน ·
  เลขใบคืนที่เกี่ยวข้อง
- **สรุปตามสินค้า**: ต่อสินค้า: เบิกเข้าจ๊อบ · เบิกหน้าสต็อก · ขาย POS · คืน · สุทธิ · ต้นทุน · `details[]` = วันที่ · เลขเอกสาร · เลขจ๊อบ/ทะเบียน
  หรือเลขใบเสร็จ `SL-` · จำนวน (ขาย POS ที่ยกเลิกแล้วแสดงคู่กับรายการยกเลิก ไม่หายไปเงียบๆ)
- **สรุปตามช่างผู้เบิก**: ต่อ `RequesterStaffId`: จำนวนใบ · จำนวนจ๊อบ · จำนวนชิ้นสุทธิ · ต้นทุน (POS ไม่มีผู้เบิก ไม่อยู่ในมุมมองนี้)
- ช่วงวันสูงสุด 366 วัน · วันตามเวลาไทย · `[RequireFeature]` รายงานขั้นสูง (sp1 ทดลองใช้ถูกล็อก)

**เว็บ**: `/reports/stock-usage` (เมนูรายงาน "การเบิกอะไหล่") · แท็บ 3 มุมมอง · แถวสินค้าขยายดูรายละเอียด · คลิกเลขใบเบิกเปิดเอกสารพิมพ์ซ้ำเดิม ·
คลิกเลขจ๊อบเปิดการ์ดจ๊อบ (`/jobs?job=`) · ส่งออก Excel

**เทสต์**: แยก source ถูก · หักยอดคืน · POS ที่ยกเลิก · ต้นทุนถูกตัดตาม role · ไม่เห็นข้อมูลสาขาอื่น

## [4] คืนอะไหล่ในขั้นเบิก/ซ่อมของจ๊อบ

**ตัดสินใจแล้ว**
- อ้างใบเบิก `WD-` เดิม คืนบางส่วนได้ · ของ **กลับเข้าล็อตเดิมที่ต้นทุนเดิม** · ยอดที่คืนกลับไปเป็น "คงเหลือให้เบิก" ตามที่ลูกค้าอนุมัติ
- คืนได้ = **ธุรการ/ผู้จัดการ** · **ก่อนออกใบเสร็จเท่านั้น**

**Backend** `POST /api/v1/inventory/withdrawals/{operationId}/returns`
`{ requestId, reasonCode, note?, lines: [{ catalogItemId, quantity }] }` → เอกสาร `RT-` (`PurchaseNumberCounter` kind ใหม่)
- คืนได้เฉพาะใบเบิกที่ผูก job (ISS- ที่เบิกจากหน้าสต็อกไม่อยู่ในขอบเขต)
- ยอดคืนได้ต่อสินค้า = เบิกในใบนั้น − คืนไปแล้ว · กระจายคืนเข้าล็อตตามลำดับย้อน FIFO (ล็อตที่ตัดทีหลังคืนก่อน) ด้วยต้นทุนของ movement เดิม
  — ทำแบบเดียวกับ `SaleService.VoidAsync` ที่คืนล็อตเดิมอยู่แล้ว
- `StockMovement` ประเภท `issue-return` คัด `JobId`/`RequesterStaffId`/`RequesterName` จากใบเดิม + คอลัมน์ใหม่ `SourceMovementId Guid?`
  ชี้ movement ที่ถูกคืน (migration `AddStockMovementSource`) — ใช้กันคืนเกินและให้รายงานจับคู่ได้
- `BuildWithdrawalPlan` นับเบิกแล้ว = issue − issue-return → คงเหลือให้เบิกเพิ่มขึ้นเอง
- error ใหม่: `WITHDRAWAL_RETURN_EXCEEDS` (เกินที่คืนได้) · `WITHDRAWAL_RETURN_RECEIPT_ISSUED` (ออกใบเสร็จแล้ว) · `WITHDRAWAL_RETURN_NOT_JOB` (ใบเบิกไม่ผูก job)
- RequestId กันคืนซ้ำแบบเดียวกับใบเบิก · `RowVersion` ของล็อต · `ActivityEvent` `stock.withdrawal.returned`
- เหตุผลตายตัว 4 ตัว (ยืนยันแล้ว 2026-10-25): เบิกเกิน · ไม่ได้ใช้ (ลูกค้ายกเลิก/เปลี่ยนใจ) · ผิดรุ่น/ผิดรายการ · อื่นๆ (บังคับหมายเหตุ)
- **ของชำรุดไม่รับคืนในรอบนี้** (ระบบยังไม่มีการปรับยอด/ตรวจนับ) — คืนได้เฉพาะของสภาพดี (ยืนยันแล้ว)

**เว็บ**: ประวัติใบเบิกใน `JobCardModal` ขั้นเบิกสินค้ามีปุ่ม "คืนของ" (ปิดพร้อมเหตุผลเมื่อออกใบเสร็จแล้ว/ไม่มีอะไรคืนได้) · หน้าต่างคืน: ตาราง เบิก/คืนแล้ว/คืนได้/คืนครั้งนี้ ·
พิมพ์ใบคืนสินค้า (โครงเดียวกับใบเบิก) · ใบเบิกเดิมแสดงยอดที่คืนแล้ว

## [5] รถใกล้ครบรอบบริการ: ตัวเลขที่เมนู + แจ้งเตือน

**ตัดสินใจแล้ว**
- แจ้งเตือนถึง **หน้าร้าน (FrontDesk) + ผู้จัดการ** — ระบบไม่มี role "SA" ใช้ FrontDesk แทน
- เตือน **ครั้งเดียวต่อรถต่อรอบนัด เมื่อเหลือ 7 วัน**

**Backend**
- **เปิดรายงาน `service-due` ให้ FrontDesk ด้วย** (เดิม Manager/Office) ไม่งั้นกดแจ้งเตือนแล้วได้ 403 — Office ยังเปิดได้แต่ไม่ได้รับแจ้งเตือน
- `GET /api/v1/reports/service-due/count` = รถที่วันนัด ≤ วันนี้ + 7 และ ≥ วันนี้ − 30 (ยืนยันแล้ว — ตรงกับขอบล่างค่าเริ่มต้นของรายงาน) กฎตัดคันเดิม
- ชนิดแจ้งเตือนใหม่ `service.due` · `AudienceRoles = FrontDesk | Manager` · `SubjectKey = service-due:{vehicleId}:{dueOn}` (กันซ้ำ) ·
  ข้อความระบุทะเบียน + รายการที่ครบ (หลังทำ [2]) · กดแล้วเปิด `/reports/service-due` พร้อมช่วงวัน ·
  **ปิด (`ResolvedAt`) เมื่อรถคันนั้นถูกเปิดจ๊อบใหม่** (แบบ "รออนุมัติ" ที่ปิดเมื่อมีคนจัดการ)
- งานรายวันใหม่ `ServiceDueDailyJob` (`BackgroundService` ใน API แบบ `SelfServeDailyJob`) 08:00 เวลาไทย + รอบแรกตอนสตาร์ต ·
  ไล่ทุกสาขาที่มีใบส่งมอบใน `GarageService` และใน `GarageSelfServe` (ผ่าน `IShardScopeFactory.RunAsAsync`) ·
  idempotent ด้วย `SubjectKey` จึงรันซ้ำได้ ไม่ต้องมีตาราง claim · ปิดได้ด้วย `ServiceDue:Jobs:Enabled=false`
- ไม่ส่งเตือนย้อนหลังให้ใบส่งมอบที่วันนัดผ่านไปแล้วตอนเปิดใช้ครั้งแรก (เตือนเฉพาะที่อยู่ในหน้าต่าง 7 วันพอดี · ยืนยันแล้ว) — รถที่เลยไปแล้วดูจากตัวเลขเมนู/รายงาน

**เว็บ**: ตัวเลขข้างเมนู "รถใกล้ครบรอบบริการ" (เห็นเฉพาะ role ที่เปิดรายงานได้) · การ์ดแจ้งเตือนชนิดใหม่

**มือถือ**: กระดิ่งรู้จัก `service.due` แสดงข้อความ และบอกว่าเปิดรายงานบนเว็บ (แบบ PR/PO) — แอปไม่มีรายงานนี้

**เทสต์**: นับตรงกับรายงาน · เตือนครั้งเดียวต่อรอบ · ไม่เตือนคันที่มีจ๊อบเปิดอยู่ · resolved เมื่อเปิดจ๊อบ · แยก shard

**[RISK]**: งานรายวันอ่าน `GarageService` ทุกสาขาในครั้งเดียว ต้องดู query plan กับข้อมูลจริง (มี filtered index บน `NextServiceDueOn` แล้ว)

## [6] แอปมือถือ: ผู้ดูแลระบบสลับสาขา

**ตัดสินใจแล้ว**: สลับจากแอปได้ **token แบบมือถือ (อายุยาว)** เหมือนตอน login

**Backend**: **ไม่ต้องแก้** — `AuthService.SwitchBranchAsync` (`AuthService.cs:471`) ออก `IssueMobileToken` อยู่แล้วเมื่อคำขอมาจาก `X-Client-Source: mobile` ·
กติกาบัญชีปลายทาง (ชื่อตรง + `IsAdministrator=1` + สาขากลุ่ม Service) และ `ActivityEvent auth.branch_switched` ใช้ของเดิม

**มือถือ**
- `User` model อ่าน `isAdministrator` (ตอนนี้แอปไม่ได้อ่าน) · `auth_api.dart` เพิ่ม `switchableBranches()` / `switchBranch(branchId)`
- หน้าโปรไฟล์: แถว "สาขา" มีปุ่ม "สลับสาขา" เฉพาะ admin → bottom sheet รายชื่อสาขา (ค้นหาเมื่อ > 6) · สาขาปัจจุบันมีป้ายกดไม่ได้
- สลับสำเร็จ: บันทึก session ใหม่ → provider ที่ `watch(sessionProvider)` รีเซ็ตเอง (แจ้งเตือน · จับเวลา · ป้ายแชท) → ล้าง cache รูป/คิว → กลับหน้าแรก + snackbar บอกบัญชีที่ใช้
- ถ้ามีคาบจับเวลาเปิดอยู่: ถามยืนยันก่อน (คาบยังเปิดค้างที่สาขาเดิม)
- sp1 ทดลองใช้: ฟีเจอร์หลายสาขาถูกล็อก — ไม่แสดงปุ่ม หรือแสดงเหตุผล `PLAN_FEATURE_LOCKED`
- 403 `AUTH_BRANCH_FORBIDDEN` แสดง `messageTh` + traceId
- bump เวอร์ชันแอป + ปล่อย store

**เทสต์**: widget test ปุ่มแสดงเฉพาะ admin · สลับแล้ว provider รีเซ็ต · ทดสอบบน simulator กับบัญชี admin จริง (เว็บยังไม่เคยทดสอบกับ Garage DB จริง — ดู `[RISK]` ใน CLAUDE.md)
